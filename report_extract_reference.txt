3. Work Progress Summary
Project Title:  MaintAI — An AI-Powered Progressive Web Application for Industrial Maintenance Assistance.
b) Brief Overview of Work Completed After Reporting 1
When I wrapped up Reporting 1, MaintAI was still mostly wireframes and a rough sketch of what the database tables should look like. Since then it has turned into an application I can actually click through end to end, even if a few screens are still half-built. I spent the first couple of weeks of this phase just getting the Next.js 14 project set up properly with the App Router, TypeScript, and Tailwind, and wiring it to Supabase for the database and auth, before touching any of the AI-facing features — it felt safer to get the boring plumbing right first rather than bolt it on later.
Authentication was the first real module I finished. I used Supabase Auth for login and signup rather than rolling my own, mainly because handling password resets and session tokens correctly is easy to get wrong, and Supabase already does it well. On top of that I added three roles — technician, supervisor, and admin — which control what a signed-in user actually sees. A technician lands on the scanner and dashboard; a supervisor also gets the analytics and inventory views; an admin can manage other users. Getting the role checks consistent across both the UI and the API routes took a bit of back-and-forth, since it's easy to hide a button in the interface and forget to guard the route behind it too.
The dashboard came next, and it's deliberately simple right now — a status overview of machines (operational, under maintenance, faulty) with a few quick-action cards. It pulls straight from Supabase and doesn't do anything clever yet; the plan is to layer the analytics screen on top of the same data once that module is further along.
QR scanning was one of the more fiddly pieces to get working reliably. I'm using the html5-qrcode library to read a machine's QR code through the device camera and resolve it to that machine's record in the database. It worked fine on my laptop almost immediately, but testing it on an actual phone browser surfaced a handful of camera-permission issues I hadn't hit before, which pushed me to add clearer handling around permission prompts and a fallback message when the camera can't be accessed.
The feature I'm probably most pleased with so far is the AI-based machine identification screen. A technician can point their camera at a machine, take a photo, and the app sends it off to either OpenAI's GPT-4o or Google Gemini — whichever provider is configured — and gets back a ranked list of likely matches with confidence scores, which the technician can then confirm or correct. Alongside that, I built FixBot, a simple chat assistant for troubleshooting questions, using the same provider abstraction. Since not everyone testing the app has an API key set up, both features fall back to a canned, non-AI response when no key is configured, so the rest of the app still works for demo purposes without an active subscription.

4. Implementation Description
explain:
Algorithm / Method Followed: For the AI-backed features, I send a structured prompt (plus the image, for machine identification) to whichever provider is configured — OpenAI's GPT-4o or Google Gemini — and parse the JSON that comes back into the shape the UI expects. If a request fails, or no API key is set at all, the app doesn't just error out; it falls back to a simpler, non-AI response so the rest of the demo still holds together.
Coding / Development Details: The whole thing is built on Next.js 14 with the App Router and TypeScript throughout. I split the routes into a public section (landing, login, signup) and an authenticated section (dashboard, scan, identify, chat), and pulled anything reused across those — API clients, Supabase helpers, type definitions — into a shared lib/ folder so I wasn't copy-pasting the same fetch logic into every page.
Database Design: The Postgres schema in Supabase covers factories, profiles, machines, repair procedures, maintenance logs, and parts, with foreign keys tying maintenance logs back to both a machine and a technician. I added Row Level Security policies early rather than as an afterthought, so a technician's queries are scoped to their own factory at the database level instead of relying on the frontend to filter correctly.
API Integration: I built dedicated API routes for chat, machine identification, and CRUD operations on machines, parts, and procedures, rather than calling Supabase directly from client components everywhere. The OpenAI SDK handles GPT-4o calls, and Gemini is wired in as an alternate provider behind the same interface, so switching between them is a config change rather than a code change.
Testing Performed: Testing so far has been manual rather than automated — going through each screen and API route myself, with the AI provider both configured and unconfigured, to make sure the fallback paths actually work and not just the happy path. I also ran ESLint regularly during development to catch obvious mistakes before they piled up.
